# 校稿提案、待處理清單與對照

> 擁有範圍：Agent 校稿結果如何存成提案、逐項套用、observations、中文 diff、
> 待處理清單與對照的行為。
> 程式：`src/core/review-apply.ts`、`src/core/word-diff.ts`、`src/core/diff.ts`（`computeComparison`）、
> `src/ui/components/panels/ReviewPanel.tsx`、`CompareView.tsx`、`src/ui/lib/stage-view.ts`、
> migration 003、`src/agents/output-contract.ts`（observations）。
> 為什麼改成提案制：[ADR-0002](../adr/0002-review-as-proposal.md)。

## 統一模型：待處理清單

校稿與查證回來的東西**不是同一種**，但可以用同一個容器裝：

| | 右側那一項是什麼 | 能不能對照 |
| --- | --- | --- |
| 校稿 | 同一篇文章的另一個版本 | 可以，這正是 diff |
| 查證 | 關於某句話的證據 | **不行**，它不是文章的版本 |

查證結果沒有「另一版文章」可以跟原稿對齊。硬塞進 diff 的右欄，那一欄會變成
一堆對不上位置的碎片。

**但兩者都是「掛在文章某一段上的待辦事項」**，所以右側永遠是同一張清單。
點任何一項，主區跳到對應段落並標亮；差別只在那一項給的按鈕。

```
待處理 (5)

✓  錯字「不彷」→「不妨」                 [套用]
⚠  語氣被改動「我覺得」→「我認為」        [套用] [略過]
◇  第 3 段與第 7 段的年份矛盾            [跳到該段]
🔍 「研究顯示…」查無出處                 [看證據]
🔍 引言查證：出自《國富論》第 4 章        [看證據] [插入註解]
```

使用者的心智模型只有一個：**清單從上往下清完，就可以發了。**

## 校稿存成提案

Agent 的輸出存成**提案**（`review_proposals` / `review_items`），內容一個字都不動，
使用者逐項決定要不要套用。

連帶的兩個變化：

- **校稿本身不讓核准失效。** 內容沒改，失效就不該發生；套用任何一項時才失效，
  而且是走一般的 `createRevision`，跟手動編輯同一條路。
- **`AgentRunResult` 沒有 `revision` 欄位了**，換成 `review`。

### 逐項套用怎麼定位

`ReviewChange` 是**描述**（把 A 改成 B），不是套用的機制。所以套用是在目前的
內容上做定位與替換（`src/core/review-apply.ts`）：

1. **從目前的內容出發，只套上被勾選的那幾項。** 反過來做（拿 Agent 的整份輸出
   再還原沒勾的）會把它沒申報的改動一起帶進來。
2. **依序定位、帶著游標往前走。** 沒勾的項目也要參與定位，否則第二個「的」
   會被套到第一個「的」的位置上。已套用過的項目找 `after`。
3. **只在標籤外面找。** 正文是 HTML 字串，`class="wp-block-paragraph"` 也是字串的
   一部分。純用 `indexOf` 的話，`before` 撞上屬性就會改到**標記**而不是文章，
   而且改出來的 HTML 仍可能通過模板 schema，沒有人會發現。
   跨過標籤邊界的（`今天<em>讀完`）也不算——換掉會把標籤吃掉。
4. **`after` 不准帶標籤。** 那是 Agent 在直接寫 HTML，那條線不開（計畫 §4.1）。
   **落在完整 `after` 裡的 `before` 不算數**（P5-T017 審查）：「很多事→很多事情」在文章已經是「很多事情」時，
   「很多事」就在改好的那句裡，照舊套下去會變成「很多事情情」。判斷方式：after＝前綴＋before＋後綴，
   而這個位置前後的字剛好補成整個 after（`isInsideAligned`，`src/contract/text-match.ts`）。跳過它之後，
   別處還有一個獨立的 before 就套到那一個——那是一個真的還沒改的出現位置，卡片的段落、字上標記
   （同一條規則）指的都是它，使用者按之前看得到會改哪裡；沒有別的就是「找不到」，再看是不是「已經改好了」。
5. **欄位照長度排，長的先找。** 照 key 順序的話 `title` 永遠排在 `body` 前面，
   一個要改正文的建議會去改標題——長文的標題本身就是一句話，撞上的機率不低。
6. **找不到就標成 `unappliable`**，明講「這一項要自己改」。猜一個位置替換下去，
   使用者不會知道文章被改到哪裡。`unappliable` 算「還沒處理」，提案不會因此結案。
7. **找不到、但文章裡已經是改好的樣子，就是「已經改好了」**（P5-T017，D-021），不是 `unappliable`。
   見下一節。

### 已經改好了（P5-T017）

原句找不到的項目，有一大類其實不用做任何事：使用者早就自己改掉了，或 AI 是從過期的稿子挑出來的
（D-021 之前 prompt 會多帶一份最早貼上的原稿）。標成「找不到」只會讓人以為還有事要做。

**規則**（`isAlreadyDone`，`src/core/review-apply.ts`）：定位跟套用**完全一樣**（逐字、只在標籤外、跨標籤不算），
以下全部成立才算：

1. `before` 在目前內容裡找不到（落在完整 after 裡的不算找到，見上面第 4 條）；
2. `after` 找得到；
3. `after` 至少 6 個字母或數字（`\p{L}\p{N}`，標點與空白不算）——「的時候，」「好的，我」到處都有，
   AI 引用時標點抄錯的話錯字可能還在，找到說明不了什麼；
4. `after` 不是 `before` 的一部分——刪字建議的 after 本來就在原文裡；
5. `before` 不是空的。

不限縮在「那一段」：段落是靠 `before` 定位的，before 找不到就沒有那一段，只能整篇找，所以靠 3、4 壓誤判。
誤判的代價也小——before 已經不在文章裡，那一項本來就套不上。

**讀取時算，不存**（跟 `blockIndex` 一樣）：`ReviewItem.alreadyDone` 為真時 `state` 回 `skipped`、`resolvedAt` 是 null，
資料庫裡的狀態不動。所以舊提案打開就對，GET 也不寫資料；內容被改回去（after 不見了）那一項就回到原本的狀態。
重判對象是還沒處理的（`pending`／`unappliable`）與按過「保留原文」的（字已經改好了還寫「保留原文」是在說謊）；
已接受、「自己改了」不重判。清單的 `pendingCount`、`blockers`、總覽的 `pendingReviewCount` 共用同一個判斷
（`openReviewRows`）。按「接受」時碰到的回在 `ReviewResolveResult.alreadyDone`，不建版本，資料庫狀態也不動。

**自動結案只看存下來的狀態**：「已經改好了」是推算的，拿它結案等於用推算的結果把提案永久關掉，文章改回去
卡片也回不來。所以剩下的都「已經改好了」時提案仍開著（清單寫「建議都處理完了」，`pendingCount` 是 0，
不擋也不提醒發布），要等使用者丟掉提案或下一次校稿取代它。

「全部接受」是**另一條路**：直接採用 Agent 交回來的整份 `templateData`，包含它
沒列進清單的調整。提案之後內容被改過（`stale`）就擋下來——那是整份覆蓋，中間的
修改會無聲消失。逐項套用不受 `stale` 影響，找不到就誠實回報。

**逐項套用不能把過期的提案變回未過期**（P5-T019，審查 #8）。套用成功會建新版本，提案的比對基準
（`base_content_hash`）要不要跟著換到新版本，看套用**之前**提案是不是已經過期：

- 還沒過期：換。這次的改動是我們自己造成的，不算外力，之後仍可「全部接受」。
- 已經過期（中間有手改、插圖、換封面）：不換，提案維持 `stale`，「全部接受」照樣擋下。
  換了等於把中間那次修改洗掉，整份採用會用 Agent 當時看到的舊稿把它蓋掉。剩下的項目仍可逐項套用。

## observations：不需要網路就能做的檢查

目前的 `ReviewOutput.changes` 形狀是「把 A 改成 B」。使用者要的「第 3 段跟
第 7 段矛盾」不是字詞替換，是一個要人判斷的觀察，現在沒地方放。

```ts
interface Observation {
  readonly kind: 'contradiction' | 'unsupported-claim' | 'missing-source' | 'gap';
  /** 對應正文第幾個頂層區塊，讓 UI 把它掛到那一段。 */
  readonly blockIndex: number;
  /** 原文中被指涉的片段，用來標亮。 */
  readonly excerpt: string;
  readonly detail: string;
  /** 建議怎麼處理；不是自動套用的改動。 */
  readonly suggestion: string;
}
```

加進 `REVIEW_OUTPUT_SCHEMA` 的 `observations` 陣列。**是新增欄位，既有測試不受影響。**

沒有網路也做得到的例子：

- 「這裡宣稱『研究顯示…』，但沒有註明是哪個研究」
- 「前面寫 1985 年，第 7 段寫 1987 年，指的是同一件事」
- 「這句引言用了引號，但沒有標出處」

也就是**把需要查的東西列出來，不假裝自己查過了**。

## 主區的檢視（B 版，D-013；D-018 拿掉三段切換）

| 畫面 | 怎麼到 | 用途 |
| --- | --- | --- |
| **文章**（預設） | 打開稿件就是 | 讀整篇；待處理的建議標在字上，上一版的改動標在頁邊 |
| **對照** | 校樣工具列「對照 AI 提案」／「對照上一版」（依比對對象），再按「回到文章」回來 | git diff 式單欄（D-019）：只列改過的段落，說明正文以外改了什麼（有提案跟提案比，沒有就跟上一版比） |
| **成品** | 只在發布面板打開時自動出現 | 跟網站上一模一樣，什麼都不標；核准前一定是這個畫面 |

沒有切換列：成品不是能選的檢視，關掉發布面板就回到原本的文章或對照。對照蓋在校樣上，校樣不卸載。
不要再加別的檢視——查證的發現跟校稿建議一起掛在右欄。畫面細節見 [design-system.md](design-system.md)。

### 對照畫面長什麼樣（D-019）

單欄，像 git diff，不是左右兩欄各列一次全文（改動會淹沒在沒變的段落裡）：

- **最上面一句先講結論**：正文改了幾段、新增幾段、刪掉幾段，以及正文以外的改動（`Comparison.fieldChanges`：
  標題、網址片段、分類／標籤等 templateData 欄位、精選圖片）。正文沒變時直接講「正文沒變，只設了精選圖片」（原本沒有＝設了、拿掉＝拿掉了、兩邊都有＝換了），
  不再寫「兩邊一模一樣」。下面逐項列「欄位：舊值 → 新值」。
- **只列有改的段落**（改寫／新增／刪除，以及文字一樣但標記改了、帶 `note` 的列「改了標記」），每列標「第 N 段」。
  段號以**目前的文章**為準，跟卡片的 `blockIndex` 同一套：跟上一版比時是右邊那一版，跟提案比時是左邊；
  目前的文章裡沒有的段落講「原第 N 段」（上一版刪掉的）或「提案第 N 段」（提案新增的）。
- **連續沒變的段落收成一行**「⋯ 第 a–b 段沒變（n 段）⋯」，點了展開、再點收起。
- 段內改動直接標在句子裡（`CompareRow.segments`）：刪掉的紅色刪除線、加上的綠色底線；整段新增／刪除整段標色。
- 點右欄卡片：捲到那一段並框出來；那一段被收起來的話先自動展開那一組。
- 收合與摘要的規則在 `src/ui/lib/diff-view.ts`（有測試）；欄位名稱與值的顯示方式只在後端
  `src/core/field-diff.ts` 決定（精選圖片給檔名＋替代文字，不給 id；本機沒存原始檔名，還沒上傳的圖只有替代文字）。
  跟提案比時不比精選圖片：提案不動它。

### 對照與逐項套用的粒度

**不是「選左邊那一版還是右邊那一版」。** 整篇二選一代表 Agent 改了 9 個地方、
8 個對 1 個把原意改掉了，使用者只能全收或全退。

正確粒度是**逐條**。資料結構已經有了：`ReviewChange` 帶 `before` / `after` /
`reason` / `meaningChanged`。**`meaningChanged` 為真者必須標紅且預設不套用**（本檔規則）。

## `blockIndex` 每次讀取時重算

`ReviewItemView.blockIndex` **每次讀取時重算**，不是存下來的：內容改過之後，
存下來的索引會指到別的段落，使用者按了跳轉會跳到錯的地方。定位不到就是 null，
那一項沒有跳轉按鈕——**包括 observation**，它自帶的 `blockIndex` 是 Agent 看它
那一版時算的，不拿來充數。

**定位忽略所有空白**（`src/contract/text-match.ts`，前後端共用）：Agent 引用原文時會自己在中文與
數字、英文之間加空格（「佔 40%」對「佔40%」），逐字比對會漏掉（P5-T008）。只用在定位與字上標記；
逐項**套用**照舊逐字比對。

同一套規則也用在 AI 內文配圖的錨點（P5-T016，見 [agent-tasks.md](agent-tasks.md)「內文圖的錨點」），
差別是那邊要動正文，所以**只有一段對得上才算數**（`findBlocksContaining`），兩段以上就不猜。

**從卡片進去直接改文章、存檔成功，那一項就結案**（P5-T012）：狀態 `skipped`，但帶著結案的 `revision_id`，
所以畫面分得出「自己改了」（`resolvedByEdit`）與「保留原文」。沒有實質改動就不結案。

已處理清單的四種下場：已接受（`applied`）、已經改好了（`alreadyDone`）、自己改了（`resolvedByEdit`）、保留原文（其餘的 `skipped`）。

**真的找不到的卡片**（`unappliable`）：直接寫「文章裡找不到「before」」，給「自己改」與「保留原文」，沒有「再試一次」
（找不到的原因是文章裡沒有那句話，重按一次結果一樣；文章改成 AI 要的樣子之後會自動變成「已經改好了」）。
從這種卡片（或任何定位不到段落的卡片）按「自己改」，游標放文章開頭，頂端講「文章裡找不到「…」，游標放在文章開頭」——
字上標不出來、段落也框不出來，不講的話使用者會以為游標停的地方就是要改的地方。

## 中文 diff

Git 那種靠空格切詞的 diff 套到中文會退化成逐字比對，產出一堆碎片
（`今[天]讀完[了]這本書`）。所以先用 `Intl.Segmenter`（`granularity: 'word'`，
Node 內建、有完整 ICU）斷詞，再對「詞」做 LCS——`src/core/word-diff.ts`。
**這是不特別處理就會默默產出垃圾的地方。**

比對一律在**後端**算：斷詞與區塊拆解後端都做了而且有測試，前端再寫一份只會得到
兩套不一樣的「第 n 段」。每一列帶完整的差異序列 `segments`（same／removed／added 照順序），
單欄畫面直接照畫；`left`／`right` 是同一串拆成兩邊的版本，保留給需要分邊的用途。

## 畫面

階段 6 的查證發現**不會**再開新的檢視——它跟校稿改動一起掛在右欄的建議清單上。

**標在字上。** 校樣在 sandbox iframe 裡（沒有 allow-scripts）。外層把待處理項目的
`before`（改動）或 `excerpt`（觀察）包進 `<mark>`，顏色用 CSSOM 設定——文件的 CSP 擋的是
`<style>` 與 style 屬性，不管外層透過 CSSOM 改樣式。只在單一文字節點裡找第一個相符的字，
跨標籤的不標，跟逐項套用的定位規則一致。點標記的事件由外層掛在文件上；判斷目標時不能用
`instanceof Element`（iframe 的節點屬於另一個視窗）。

**卡片跟標記一對一。** 點卡片：文章捲到那段字並框出所在段落；點文章裡的標記：右欄那張卡片
亮起來並捲進畫面。

**「按了就好」的一群。** Agent 自己說不改變原意的錯字有兩項以上時，收成一張「錯字 ×N」卡片，
一鍵全部接受，也可以展開一項一項看（Q-3 的現行預設）。`meaningChanged` 為真的永遠單獨一張卡片，
標「可能改變原意」。

切到對照時，校樣**不卸載**，只是 `visibility: hidden` 被蓋住。用 `display: none` 會讓
iframe 的版面歸零，`ResizeObserver` 隨即把量到的段落位置全部洗成 0，圖片區的
「把圖片插在第 n 段後面」就會指到錯的地方。

建議清單是右欄本身，不是一張收起來的卡片；核准與發布的入口在頂列的「發布…」，不會被清單擋住。
處理過的項目收進「已處理 N 項」（Q-2 目前的做法：留著但收起來）。

`blockers` 會多一條「還有 N 項校稿建議沒處理」。那是**提醒不是禁令**——`blockers`
只餵給畫面，發布的硬性前置檢查仍然只在 `preflightPublish`。

畫面上「套用」與「略過」**共用同一個 busy 旗標**：各自一個的話兩個請求會疊在
同一項上。後端也擋了（已套用的項目不接受「略過」，否則文字還在但清單說沒套用），
兩層都要有——畫面那層是不讓它發生，後端那層是它還是發生了的時候不說謊。
